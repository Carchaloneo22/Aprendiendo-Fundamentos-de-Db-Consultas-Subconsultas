01

¿Por qué reglas de integridad?

⏱ 15 min de lectura

Imagina que la tabla productos no tiene ninguna regla. ¿Qué podría pasar?

Lo que alguien podría insertarEl desastre que causa
Un producto sin nombre (NULL).No sabes qué estás vendiendo.
Dos productos llamados exactamente "Empanada".Duplicados, confusión en inventario y reportes.
Un precio de -50.El sistema calcularía ventas negativas: pierdes dinero en pantalla.
Una cantidad de -3 unidades.El inventario se rompe.
Dos filas con el mismo id (si no fuera IDENTITY).No puedes distinguir una fila de otra.
Integridad de datos significa que los datos guardados son válidos, consistentes y confiables. Las reglas de integridad son las barreras que SQL Server coloca para que ningún dato inválido pueda entrar, sin importar quién escriba el INSERT.

El concepto clave: CONSTRAINT

Cada regla que agregamos se llama CONSTRAINT (restricción). Cada una tiene un nombre, y es buena práctica nombrarlas con una convención:

PrefijoTipo de reglaEjemplo
PK_PRIMARY KEYPK_productos
UQ_UNIQUEUQ_productos_nombre
DF_DEFAULTDF_productos_activo
CK_CHECKCK_productos_precio
💡 ¿Por qué nombrarlas?Si no les pones nombre, SQL Server genera nombres horribles como PK__producto__3213E83F1A2B3C4D. Con nombres claros, cuando ocurra un error sabrás exactamente qué regla se violó.
02

PRIMARY KEY: la cédula de cada fila

⏱ 25 min práctica

La PRIMARY KEY (clave primaria) convierte a una columna en el identificador único de cada fila. SQL Server la protege con dos reglas automáticas: UNIQUE (no puede repetirse) y NOT NULL (no puede faltar).

Convirtamos el id de productos en PK oficial

  productos_con_pk.sql
CREATE TABLE productos (
    id                INT IDENTITY(1,1)
        CONSTRAINT PK_productos PRIMARY KEY,
    nombre            VARCHAR(80),
    precio            DECIMAL(10,2),
    cantidad          INT,
    fecha_vencimiento DATE,
    activo            BIT
);
Command(s) completed successfully.

Si ya tenías la tabla de BD·103 sin PK, puedes agregarla así:

  agregar_pk.sql
ALTER TABLE productos
ADD CONSTRAINT PK_productos PRIMARY KEY (id);

Probemos romperla a propósito

Como id es IDENTITY, no podemos duplicarlo manualmente. Pero si intentáramos insertar un NULL en la PK (cosa que IDENTITY tampoco permite), veríamos este error:

Msg 515, Level 16 — Cannot insert the value NULL into column 'id', table 'tienda_db.dbo.productos'; column does not allow nulls. INSERT fails.

Traducción: "No puedo guardar NULL en la columna id porque no lo permite. El INSERT falló." SQL Server acaba de proteger tu tabla.

🔑 Regla de oroUna tabla debe tener siempre una clave primaria. Si no la tiene, es como una persona sin documento de identidad: existe, pero no puedes distinguirla de otras.
03

NOT NULL y DEFAULT: obligatorios y automáticos

⏱ 20 min práctica

NOT NULL: campos que no pueden quedar vacíos

Algunos campos son esenciales. Un producto debe tener nombre y precio. Para eso usamos NOT NULL:

  campos_obligatorios.sql
CREATE TABLE productos (
    id                INT IDENTITY(1,1) CONSTRAINT PK_productos PRIMARY KEY,
    nombre            VARCHAR(80)   NOT NULL,   -- obligatorio
    precio            DECIMAL(10,2) NOT NULL,   -- obligatorio
    cantidad          INT           NOT NULL,   -- obligatorio
    fecha_vencimiento DATE          NULL,       -- opcional (algunos no vencen)
    activo            BIT           NOT NULL    -- obligatorio
);

Si alguien intenta insertar un producto sin nombre:

INSERT INTO productos (nombre, precio, cantidad, activo)
VALUES (NULL, 2500, 10, 1);
Msg 515 — Cannot insert the value NULL into column 'nombre', table 'tienda_db.dbo.productos'; column does not allow nulls.

DEFAULT: el valor que aparece si no lo escribes

Un producto nuevo casi siempre está activo. En lugar de escribir 1 cada vez, ponemos un DEFAULT:

  default_activo.sql
activo BIT NOT NULL
    CONSTRAINT DF_productos_activo DEFAULT 1

Ahora puedes omitir la columna activo, y SQL Server pone 1 automáticamente:

INSERT INTO productos (nombre, precio, cantidad)
VALUES ('Empanada', 2500, 30);
-- activo queda en 1 gracias al DEFAULT
💡 DEFAULT con fechasPara registrar "cuándo se creó un registro", usa GETDATE(): fecha_registro DATETIME2 DEFAULT GETDATE(). SQL Server pondrá la fecha y hora del servidor automáticamente.
04

UNIQUE: campos que no pueden repetirse

⏱ 15 min práctica

A veces quieres que una columna no sea la clave primaria, pero tampoco permita duplicados. Por ejemplo: dos productos no deberían llamarse exactamente igual.

  unique_nombre.sql
ALTER TABLE productos
ADD CONSTRAINT UQ_productos_nombre UNIQUE (nombre);

Probemos duplicar un nombre

-- Supongamos que ya existe una 'Empanada'
INSERT INTO productos (nombre, precio, cantidad, activo)
VALUES ('Empanada', 3000, 20, 1);
Msg 2627, Level 14 — Violation of UNIQUE KEY constraint 'UQ_productos_nombre'. Cannot insert duplicate key in object 'dbo.productos'. The duplicate key value is (Empanada).

SQL Server nos dice exactamente qué regla se violó y cuál es el valor duplicado. Esto es oro puro para depurar.

UNIQUE vs PRIMARY KEY

CaracterísticaPRIMARY KEYUNIQUE
¿Cuántas por tabla?Solo 1Varias
¿Acepta NULL?NoSí (uno solo)
¿Se usa como identificador principal?SíNo
05

CHECK: rangos y condiciones válidas

⏱ 20 min práctica

La regla más flexible. Puedes escribir cualquier condición que los datos deban cumplir. El ejemplo clásico: el precio no puede ser negativo ni cero.

  check_precio.sql
ALTER TABLE productos
ADD CONSTRAINT CK_productos_precio CHECK (precio > 0);

Provocando el error

INSERT INTO productos (nombre, precio, cantidad, activo)
VALUES ('Producto fantasma', -50, 5, 1);
Msg 547, Level 16 — The INSERT statement conflicted with the CHECK constraint "CK_productos_precio". The conflict occurred in database "tienda_db", table "dbo.productos", column 'precio'.

Más ejemplos de CHECK

-- La cantidad no puede ser negativa
ADD CONSTRAINT CK_productos_cantidad CHECK (cantidad >= 0);

-- El activo solo acepta 0 o 1 (BIT ya lo limita, pero es explícito)
ADD CONSTRAINT CK_productos_activo CHECK (activo IN (0, 1));

-- Si hay fecha de vencimiento, debe ser en el futuro al momento de crear
-- (esto se valida al INSERT/UPDATE, no es perfecto, pero sirve)
ADD CONSTRAINT CK_productos_fecha CHECK (fecha_vencimiento IS NULL OR fecha_vencimiento >= GETDATE());
💡 CHECK vs validación en la aplicaciónCHECK protege los datos en la base, sin importar quién escriba el INSERT. Es tu última línea de defensa. Nunca confíes solo en la validación del frontend.
06

Ver tus reglas: sp_helpconstraint y SSMS

⏱ 10 min práctica

Para ver todas las restricciones de una tabla:

  ver_restricciones.sql
EXEC sp_helpconstraint 'productos';

Verás una lista con el nombre de cada constraint, su tipo y la definición. También puedes hacerlo con el ratón: clic derecho sobre la tabla → Design → clic derecho en la cuadrícula → Indexes/Keys o Check Constraints.

Borrar una restricción

ALTER TABLE productos
DROP CONSTRAINT UQ_productos_nombre;
🚨 CuidadoQuitar una restricción es rápido, pero también elimina la protección. Hazlo solo si realmente ya no la necesitas, y documenta el porqué.
Resumen visual: una tabla robusta tiene PK (identidad), NOT NULL (campos obligatorios), DEFAULT (valores automáticos), UNIQUE (sin duplicados) y CHECK (rangos válidos). Juntas forman la armadura de tus datos.

E2

Blindar productos · en el computador

⏱ 25 min · individual

Si ya tienes la tabla productos de BD·103, agrégale estas restricciones. Si no, créala desde cero con todo incluido:

  • PK en id.
  • NOT NULL en nombre, precio, cantidad y activo.
  • DEFAULT 1 en activo.
  • UNIQUE en nombre.
  • CHECK: precio mayor que 0.
  • CHECK: cantidad mayor o igual a 0.

Luego ejecuta EXEC sp_helpconstraint 'productos'; y verifica que aparezcan todas.

🔍 Script completo 
CREATE TABLE productos (
    id                INT IDENTITY(1,1)
        CONSTRAINT PK_productos PRIMARY KEY,
    nombre            VARCHAR(80)   NOT NULL,
    precio            DECIMAL(10,2) NOT NULL,
    cantidad          INT           NOT NULL,
    fecha_vencimiento DATE          NULL,
    activo            BIT           NOT NULL
        CONSTRAINT DF_productos_activo DEFAULT 1,

    CONSTRAINT UQ_productos_nombre   UNIQUE (nombre),
    CONSTRAINT CK_productos_precio   CHECK (precio > 0),
    CONSTRAINT CK_productos_cantidad CHECK (cantidad >= 0)
);

E4

🏆 Reto: el refugio Patitas, blindado

⏱ 35 min · parejas

Toma la tabla mascotas del refugio Patitas (BD·103) y aplícale un conjunto completo de reglas. Requisitos:

  • PK en id.
  • NOT NULL en nombre, especie y fecha_ingreso.
  • DEFAULT: si no se indica, fecha_ingreso es hoy (pista: GETDATE()).
  • UNIQUE en nombre (dos mascotas no pueden llamarse igual en el refugio).
  • CHECK: peso_kg mayor que 0.
  • CHECK: especie solo acepta 'Perro', 'Gato', 'Ave' u 'Otro'.

Luego inserta una mascota válida y una inválida (especie 'Dinosaurio'), y captura ambos resultados.

✏️ Espacio para tu script y capturas.
🔍 Solución completa 
CREATE TABLE mascotas (
    id               INT IDENTITY(1,1)
        CONSTRAINT PK_mascotas PRIMARY KEY,
    nombre           VARCHAR(60)  NOT NULL,
    especie          VARCHAR(40)  NOT NULL,
    fecha_nacimiento DATE         NULL,
    peso_kg          DECIMAL(5,2) NULL,
    vacunada         BIT          NOT NULL CONSTRAINT DF_mascotas_vacunada DEFAULT 0,
    fecha_ingreso    DATE         NOT NULL
        CONSTRAINT DF_mascotas_ingreso DEFAULT GETDATE(),

    CONSTRAINT UQ_mascotas_nombre  UNIQUE (nombre),
    CONSTRAINT CK_mascotas_peso    CHECK (peso_kg > 0),
    CONSTRAINT CK_mascotas_especie CHECK (especie IN ('Perro','Gato','Ave','Otro'))
);

-- Inserción válida
INSERT INTO mascotas (nombre, especie, peso_kg)
VALUES ('Rocco', 'Perro', 18.4);

-- Inserción inválida (fallará)
INSERT INTO mascotas (nombre, especie, peso_kg)
VALUES ('Rex', 'Dinosaurio', 500);

El segundo INSERT devuelve un error Msg 547 mencionando CK_mascotas_especie. La tabla acaba de rechazar un dinosaurio. Misión cumplida. 🦖🚫

Mini glosario de esta entrega

Consulta rápida
Integridad de datos
Garantía de que los datos almacenados son válidos, consistentes y confiables.
CONSTRAINT
Regla declarada sobre una columna o tabla para proteger los datos. Cada una tiene un nombre.
PRIMARY KEY
Columna (o conjunto) que identifica de forma única cada fila. Es UNIQUE y NOT NULL a la vez.
UNIQUE
Restricción que impide valores duplicados en una columna, a diferencia de la PK sí acepta un NULL.
NOT NULL
Obliga a que la columna siempre tenga un valor; no permite NULL.
DEFAULT
Valor que SQL Server asigna automáticamente si el INSERT no especifica esa columna.
CHECK
Restricción que valida una condición lógica (rangos, listas IN, comparaciones) antes de aceptar el dato.
sp_helpconstraint
Procedimiento del sistema que lista todas las restricciones de una tabla.
