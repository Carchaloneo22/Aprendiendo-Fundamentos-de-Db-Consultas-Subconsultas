Los roles: padre e hijo

Rol¿Qué guarda?Ejemplo
Tabla padreLa entidad “fuerte”, de la que dependen los demás. Tiene la PK original.CATEGORIAS: Bebidas, Fritos, Snacks…
Tabla hijoLa entidad que apunta al padre. Guarda una copia del id del padre en su FK.PRODUCTOS: cada producto dice “pertenezco a la categoría 1 (Bebidas)”.
💡 Truco para detectar al padrePregúntate: ¿cuál de las dos puede existir sola, sin la otra? Las categorías existen aunque no haya productos; los productos necesitan pertenecer a una categoría. La que puede existir sola es el padre.
02

FOREIGN KEY: el puente entre tablas

⏱ 25 min práctica

Una FOREIGN KEY (clave foránea, FK) es una columna en la tabla hijo que apunta a la clave primaria de la tabla padre. Es el puente físico que convierte una relación teórica en una regla real que SQL Server protege.

Paso 1: crear la tabla padre (CATEGORIAS)

  01_categorias.sql
CREATE TABLE categorias (
    id          INT IDENTITY(1,1)
        CONSTRAINT PK_categorias PRIMARY KEY,
    nombre      VARCHAR(60) NOT NULL
        CONSTRAINT UQ_categorias_nombre UNIQUE,
    descripcion VARCHAR(200) NULL
);

Paso 2: crear la tabla hijo con la FK (PRODUCTOS)

  02_productos.sql
CREATE TABLE productos (
    id           INT IDENTITY(1,1)
        CONSTRAINT PK_productos PRIMARY KEY,
    nombre       VARCHAR(80) NOT NULL
        CONSTRAINT UQ_productos_nombre UNIQUE,
    categoria_id INT NOT NULL,
    precio       DECIMAL(10,2) NOT NULL
        CONSTRAINT CK_productos_precio CHECK (precio > 0),
    cantidad     INT NOT NULL
        CONSTRAINT CK_productos_cantidad CHECK (cantidad >= 0),
    activo       BIT NOT NULL
        CONSTRAINT DF_productos_activo DEFAULT 1,

    -- ⬇ AQUÍ ESTÁ EL PUENTE ⬇
    CONSTRAINT FK_productos_categoria
        FOREIGN KEY (categoria_id)
        REFERENCES categorias(id)
);
Command(s) completed successfully.

La anatomía de la FOREIGN KEY

ParteSignificado
CONSTRAINT FK_productos_categoriaEl nombre del puente. Convención: FK_hijo_padre.
FOREIGN KEY (categoria_id)La columna de la tabla hijo que apunta al padre.
REFERENCES categorias(id)La tabla padre y su columna clave.
⚠️ Regla de oroEl tipo de dato del FK en el hijo debe ser idéntico al tipo de la PK en el padre. Si categorias.id es INT, entonces productos.categoria_id también debe ser INT (no VARCHAR, no BIGINT).

¿Y si ya tengo la tabla creada?

Puedes agregar la FK con ALTER TABLE:

  agregar_fk.sql
ALTER TABLE productos
ADD CONSTRAINT FK_productos_categoria
    FOREIGN KEY (categoria_id)
    REFERENCES categorias(id);
03

El orden importa: crear y borrar en secuencia

⏱ 15 min práctica

Regla al crear: primero el padre, después el hijo

SQL Server no puede crear una FK que apunta a una tabla que todavía no existe. Si intentas crear productos antes de categorías:

Msg 1767, Level 16 — Foreign key 'FK_productos_categoria' references invalid table 'categorias'.

Traducción: “No puedo referenciar una tabla que no existe todavía.”

1

Crear todas las tablas padre primero

Sin ninguna FK. En nuestro caso: categorias.

2

Después las tablas hijo

Ahora sí pueden referenciar a las padre que ya existen.

Regla al borrar: primero el hijo, después el padre

Lo opuesto también es cierto. Si intentas borrar categorias mientras existen productos que la referencian:

Msg 3726, Level 16 — Could not drop object 'dbo.categorias' because it is referenced by a FOREIGN KEY constraint.

Traducción: “No puedo borrar categorías porque productos todavía la usa.”

1

Borrar primero las tablas hijo

DROP TABLE productos;

2

Después las padre

DROP TABLE categorias;

💡 Script limpio de borradoCuando tengas muchas tablas, al inicio de tus scripts coloca los DROP en orden inverso al de creación. Así puedes ejecutar el script varias veces sin errores: 
-- Borrado seguro al inicio de cada script
DROP TABLE IF EXISTS productos;   -- hijo primero
DROP TABLE IF EXISTS categorias;  -- padre después
GO
04

¿Qué pasa con los hijos cuando el padre cambia?

⏱ 20 min práctica

Cuando borras o modificas una fila del padre, ¿qué debe hacer SQL Server con los hijos que apuntaban a ella? Tienes cuatro opciones, y se declaran con ON DELETE y ON UPDATE.

OpciónQué hace con los hijosCuándo usarla
NO ACTION
(por defecto)		Bloquea el borrado/modificación del padre si hay hijos. Es el comportamiento seguro por defecto.Casi siempre: evitar que se borren datos sin pensar.
CASCADEBorra o actualiza automáticamente los hijos junto con el padre. Es una reacción en cadena.Cuando los hijos no tienen sentido sin el padre (p. ej. líneas de un pedido).
SET NULLPone en NULL la columna FK de los hijos. Requiere que el FK admita NULL.Cuando los hijos pueden quedar “sin asignar” (p. ej. empleados sin departamento).
SET DEFAULTAsigna el valor DEFAULT a la columna FK de los hijos.Casos muy específicos con un valor por defecto claro.

Ejemplo real: CASCADE para pedidos

Piensa en una tabla PEDIDO y otra DETALLE_PEDIDO. Si borras un pedido, los detalles deben desaparecer con él — no tienen sentido solos:

  cascade.sql
CREATE TABLE detalle_pedido (
    id          INT IDENTITY(1,1) PRIMARY KEY,
    pedido_id   INT NOT NULL,
    producto    VARCHAR(80) NOT NULL,
    cantidad    INT NOT NULL,

    CONSTRAINT FK_detalle_pedido
        FOREIGN KEY (pedido_id)
        REFERENCES pedidos(id)
        ON DELETE CASCADE      -- borrar el pedido borra sus líneas
        ON UPDATE CASCADE      -- si cambia el id, cambia aquí también
);
🤓 La opción por defectoSi no escribes nada, SQL Server asume NO ACTION: bloquea el cambio del padre. Es la opción más segura. Solo usa CASCADE cuando entiendas claramente que los hijos deben desaparecer junto con el padre.
05

⏱ 15 min práctica

Ya tienes categorias y productos con su FK. Insertemos algunas categorías primero:

  insert_categorias.sql
INSERT INTO categorias (nombre) VALUES ('Bebidas');   -- id = 1
INSERT INTO categorias (nombre) VALUES ('Fritos');    -- id = 2
INSERT INTO categorias (nombre) VALUES ('Snacks');    -- id = 3

Error 1: insertar un hijo con padre inexistente

Intentamos insertar un producto que apunta a la categoría 999, que no existe:

INSERT INTO productos (nombre, categoria_id, precio, cantidad)
VALUES ('Pan', 999, 1500, 20);
Msg 547, Level 16 — The INSERT statement conflicted with the FOREIGN KEY constraint "FK_productos_categoria". The conflict occurred in database "tienda_db", table "dbo.categorias", column 'id'.

SQL Server dice: “el INSERT choca con la FK. El conflicto está en la tabla categorias, columna id.” Ese es el hijo huérfano que evitamos.

Error 2: borrar un padre con hijos

Intentemos borrar la categoría “Bebidas” (id=1), que tiene productos asociados:

DELETE FROM categorias WHERE id = 1;
Msg 547, Level 16 — The DELETE statement conflicted with the REFERENCE constraint "FK_productos_categoria". The conflict occurred in database "tienda_db", table "dbo.productos", column 'categoria_id'.

Ahora el conflicto es al revés: hay hijos referenciando ese padre. SQL Server no deja borrar hasta que los hijos desaparezcan o cambien su FK.

Error 3: actualizar la PK del padre

Si intentamos cambiar el id de una categoría (algo que nunca deberíamos hacer, pero alguien podría intentar):

UPDATE categorias SET id = 99 WHERE id = 1;
Msg 547 — The UPDATE statement conflicted with the REFERENCE constraint "FK_productos_categoria".

Mismo problema: los hijos siguen apuntando al id viejo. La solución real: nunca cambies el id del padre. Es la cédula: si cambias, se rompe todo.

🔑 La lección más importanteLos errores 547 de integridad referencial no son errores del código: son el motor protegiendo tus datos. Cuando los veas, no entres en pánico: lee el mensaje, detecta la FK involucrada y decide qué hacer (insertar el padre primero, borrar los hijos primero, o usar CASCADE).

Construye la tienda completa · en el computador

⏱ 25 min · individual

Crea un script que, en el orden correcto, haga lo siguiente:

  • Borrar las tablas si ya existen (en orden correcto).
  • Crear categorias con PK, UNIQUE en nombre.
  • Crear productos con PK, UNIQUE en nombre, NOT NULL en nombre/precio/cantidad, CHECK precio>0 y cantidad>=0, DEFAULT activo=1, y la FK a categorias.
  • Insertar 3 categorías (Bebidas, Fritos, Snacks) y 5 productos (2 Bebidas, 2 Fritos, 1 Snacks).
  • Mostrar el resultado final con un SELECT.
✏️ Espacio para tu script y las capturas de los mensajes.
🔍 Script completo 
-- Borrado seguro
DROP TABLE IF EXISTS productos;
DROP TABLE IF EXISTS categorias;
GO

-- Paso 1: tabla padre
CREATE TABLE categorias (
    id          INT IDENTITY(1,1)
        CONSTRAINT PK_categorias PRIMARY KEY,
    nombre      VARCHAR(60) NOT NULL
        CONSTRAINT UQ_categorias_nombre UNIQUE,
    descripcion VARCHAR(200) NULL
);
GO

-- Paso 2: tabla hijo con FK
CREATE TABLE productos (
    id           INT IDENTITY(1,1)
        CONSTRAINT PK_productos PRIMARY KEY,
    nombre       VARCHAR(80) NOT NULL
        CONSTRAINT UQ_productos_nombre UNIQUE,
    categoria_id INT NOT NULL,
    precio       DECIMAL(10,2) NOT NULL
        CONSTRAINT CK_productos_precio CHECK (precio > 0),
    cantidad     INT NOT NULL
        CONSTRAINT CK_productos_cantidad CHECK (cantidad >= 0),
    activo       BIT NOT NULL
        CONSTRAINT DF_productos_activo DEFAULT 1,

    CONSTRAINT FK_productos_categoria
        FOREIGN KEY (categoria_id)
        REFERENCES categorias(id)
);
GO

-- Paso 3: insertar categorías primero (son el padre)

INSERT INTO categorias (nombre) VALUES ('Fritos');   -- id = 2
INSERT INTO categorias (nombre) VALUES ('Snacks');   -- id = 3
GO

-- Paso 4: insertar productos apuntando a las categorías existentes
INSERT INTO productos (nombre, categoria_id, precio, cantidad)
VALUES ('Gaseosa 400 ml', 1, 3500, 48);

INSERT INTO productos (nombre, categoria_id, precio, cantidad)
VALUES ('Café', 1, 1800, 0);

INSERT INTO productos (nombre, categoria_id, precio, cantidad)
VALUES ('Empanada', 2, 2500, 30);

INSERT INTO productos (nombre, categoria_id, precio, cantidad)
VALUES ('Arepas', 2, 2000, 15);

INSERT INTO productos (nombre, categoria_id, precio, cantidad)

-- Paso 5: ver el resultado

El SELECT final todavía usa una sintaxis “al estilo viejo” para unir las tablas — en BD·109 aprenderás la sintaxis moderna con JOIN. Pero ya puedes ver el puente funcionando: los productos muestran el nombre real de su categoría.

E4

🏆 Reto integrador: el refugio Patitas, con dueños

⏱ 35 min · equipos

“El refugio Patitas quiere registrar a sus mascotas junto con su dueño actual (si lo tiene). Cada dueño puede tener varias mascotas, pero cada mascota tiene a lo sumo un dueño registrado. Si un dueño desaparece del sistema, la mascota no se borra: queda sin dueño registrado.”

Requisitos del diseño:

  • Tabla duenos con id, nombre, telefono (UNIQUE) y correo.
  • Tabla mascotas con todas las reglas de BD·104, más un dueno_id que puede ser NULL (para mascotas sin dueño).
  • La FK con la opción correcta: cuando se borra un dueño, su FK en mascotas se pone en NULL.
  • Insertar 2 dueños y 3 mascotas (una sin dueño).
  • Probar que al borrar un dueño, su mascota queda con dueno_id = NULL (no se borra).
✏️ Espacio de borrador del equipo.
💡 Pista

La opción correcta es ON DELETE SET NULL. Y para que funcione, la columna FK debe permitir NULL: dueno_id INT NULL.

🔍 Solución completa 
-- Borrado seguro
DROP TABLE IF EXISTS mascotas;
DROP TABLE IF EXISTS duenos;
GO

-- Tabla padre: dueños
CREATE TABLE duenos (
    id       INT IDENTITY(1,1)
        CONSTRAINT PK_duenos PRIMARY KEY,
    nombre   VARCHAR(80) NOT NULL,
    telefono VARCHAR(20) NOT NULL
        CONSTRAINT UQ_duenos_telefono UNIQUE,
    correo   VARCHAR(120) NULL
);
GO

-- Tabla hijo: mascotas
CREATE TABLE mascotas (
    id               INT IDENTITY(1,1)
        CONSTRAINT PK_mascotas PRIMARY KEY,
    nombre           VARCHAR(60)  NOT NULL,
    especie          VARCHAR(40)  NOT NULL,
    fecha_nacimiento DATE         NULL,
    peso_kg          DECIMAL(5,2) NULL,
    vacunada         BIT NOT NULL
        CONSTRAINT DF_mascotas_vacunada DEFAULT 0,
    fecha_ingreso    DATE NOT NULL
        CONSTRAINT DF_mascotas_ingreso DEFAULT GETDATE(),

    -- ⬇ la columna FK admite NULL porque no todas las mascotas tienen dueño
    dueno_id         INT NULL,

    CONSTRAINT UQ_mascotas_nombre  UNIQUE (nombre),
    CONSTRAINT CK_mascotas_peso    CHECK (peso_kg > 0),
    CONSTRAINT CK_mascotas_especie CHECK (especie IN ('Perro','Gato','Ave','Otro')),
    CONSTRAINT FK_mascotas_dueno
        FOREIGN KEY (dueno_id)
        REFERENCES duenos(id)
        ON DELETE SET NULL   -- clave del requisito ✔
);
GO

-- Datos de prueba
INSERT INTO duenos (nombre, telefono)
VALUES ('Ana Torres', '310-111-2222'),   -- id = 1
       ('Bruno Díaz', '300-777-8888');   -- id = 2

INSERT INTO mascotas (nombre, especie, peso_kg, dueno_id)
VALUES ('Firulais', 'Perro', 12.5, 1);     -- de Ana
INSERT INTO mascotas (nombre, especie, peso_kg, dueno_id)
VALUES ('Misifú',   'Gato',  3.8, 2);      -- de Bruno
INSERT INTO mascotas (nombre, especie, peso_kg)
VALUES ('Rocky',    'Perro', 18.0);       -- sin dueño
GO

-- Prueba de integridad referencial: borrar a Bruno
DELETE FROM duenos WHERE nombre = 'Bruno Díaz';
GO

-- Ver qué pasó con Misifú
SELECT m.nombre, m.especie, m.dueno_id
FROM mascotas m;
-- Misifú sigue en la tabla, pero ahora su dueno_id = NULL ✔

El resultado: Firulais (dueno_id=1), Misifú (dueno_id=NULL después del DELETE) y Rocky (dueno_id=NULL desde el inicio). La integridad referencial hizo exactamente lo que pedimos: preservar al hijo y quitar su referencia al padre desaparecido.

Mini glosario de esta entrega

Consulta rápida
Tabla padre
La tabla que contiene la clave primaria referenciada. Es la entidad “fuerte” de la relación.
Tabla hijo
La tabla que contiene la clave foránea. Depende del padre para existir correctamente.
FOREIGN KEY (FK)
Columna o conjunto de columnas en el hijo que apunta a la PK del padre. Crea el puente entre ambas tablas.
Integridad referencial
Garantía de que toda FK apunte a un valor válido (existente) en el padre, o a NULL si se permite.
Hijo huérfano
Fila del hijo cuya FK apunta a un valor que no existe en el padre. SQL Server lo impide.
ON DELETE CASCADE
Al borrar una fila del padre, se borran automáticamente los hijos que la referenciaban.
ON DELETE SET NULL
Al borrar una fila del padre, la FK de sus hijos se pone en NULL.
ON DELETE NO ACTION
Comportamiento por defecto: bloquea el borrado del padre si hay hijos referenciándolo.
