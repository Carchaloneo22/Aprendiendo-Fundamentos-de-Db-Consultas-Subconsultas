01

El problema N:M: una FK no alcanza

⏱ 15 min de lectura

En una relación 1:N, ponemos una FK en el lado "muchos". Funciona perfecto:

Relación 1:NSolución
Una categoría tiene muchos productos.productos.categoria_id → categorias.id
Un dueño tiene muchas mascotas.mascotas.dueno_id → duenos.id

Pero mira lo que pasa con N:M:

Situación¿Por qué es N:M?
Un estudiante se inscribe en varias asignaturas. Una asignatura tiene varios estudiantes.No puedes poner una sola FK: ¿en qué tabla la pondrías? Si la pones en ESTUDIANTES, un estudiante solo podría tener una asignatura. Si la pones en ASIGNATURAS, una asignatura solo podría tener un estudiante. Ninguna de las dos sirve.
Una mascota es atendida por varios veterinarios. Un veterinario atiende varias mascotas.Mismo problema: la FK no cabe en un solo lado.
Cuando la relación es muchos-a-muchos, ninguna de las dos tablas puede contener la FK sola. La solución es crear una tercera tabla que contenga dos FK: una apuntando a cada lado. Esa tercera tabla se llama tabla intermedia (o tabla de unión, o tabla de detalle).
02

Relaciones 1:1: el caso menos común

⏱ 15 min práctica

Una relación 1:1 significa que una fila de la tabla A se conecta con exactamente una fila de la tabla B, y viceversa. Es menos común que 1:N, pero aparece en casos como:

  • Un usuario tiene un perfil (y un perfil pertenece a un solo usuario).
  • Un empleado tiene una hoja de vida (y una hoja de vida es de un solo empleado).
  • Un país tiene una capital (en el modelo simplificado).

Cómo se construye: FK con UNIQUE

La FK se pone en una de las dos tablas, pero se declara como UNIQUE para garantizar que no se repita:

  uno_a_uno.sql
CREATE TABLE usuarios (
    id       INT IDENTITY(1,1) PRIMARY KEY,
    username VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE perfiles (
    id            INT IDENTITY(1,1) PRIMARY KEY,
    usuario_id    INT NOT NULL UNIQUE,  -- ⬅ UNIQUE lo hace 1:1
    bio           VARCHAR(300),
    foto_url      VARCHAR(250),

    CONSTRAINT FK_perfiles_usuario
        FOREIGN KEY (usuario_id)
        REFERENCES usuarios(id)
);
💡 ¿Por qué separar en 1:1?Principalmente por rendimiento y organización: la tabla principal queda ligera, y la información secundaria se consulta solo cuando se necesita. También por seguridad: puedes dar permisos diferentes a cada tabla.
03

La tabla intermedia: el puente de puentes

⏱ 25 min práctica

Vamos a construir el caso del refugio Patitas: mascotas ↔ veterinarios. Una mascota puede ser atendida por varios veterinarios a lo largo del tiempo. Un veterinario atiende a muchas mascotas.

MASCOTAS

  • PK id
  • nombre
  • especie
⇄mascota_id

CONSULTAS

  • PK+FK mascota_id
  • PK+FK veterinario_id
  • fecha
  • diagnostico
⇄veterinario_id

VETERINARIOS

  • PK id
  • nombre
  • especialidad

Paso 1: crear las tablas "extremo"

  01_extremos.sql
CREATE TABLE veterinarios (
    id           INT IDENTITY(1,1) PRIMARY KEY,
    nombre       VARCHAR(80) NOT NULL,
    especialidad VARCHAR(60) NULL
);

-- La tabla mascotas ya existe de BD·104/BD·105

Paso 2: crear la tabla intermedia

  02_intermedia.sql
CREATE TABLE consultas (
    mascota_id     INT NOT NULL,
    veterinario_id INT NOT NULL,
    fecha          DATE NOT NULL DEFAULT GETDATE(),
    diagnostico    VARCHAR(300) NULL,

    -- Las dos FK juntas forman la PK compuesta
    CONSTRAINT PK_consultas
        PRIMARY KEY (mascota_id, veterinario_id, fecha),

    CONSTRAINT FK_consultas_mascota
        FOREIGN KEY (mascota_id)
        REFERENCES mascotas(id)
        ON DELETE CASCADE,

    CONSTRAINT FK_consultas_veterinario
        FOREIGN KEY (veterinario_id)
        REFERENCES veterinarios(id)
        ON DELETE CASCADE
);
💡 Dos cosas clave aquí① La PK es compuesta: dos (o más) columnas juntas forman la clave. ② Usamos ON DELETE CASCADE porque si se borra una mascota o un veterinario, sus consultas deben desaparecer con ellos.
04

PK compuesta: cuando una columna no basta

⏱ 20 min práctica

En la tabla consultas de arriba, ¿qué identifica de forma única a cada fila? Ninguna columna sola lo hace:

  • mascota_id se repite: una mascota tiene varias consultas.
  • veterinario_id se repite: un veterinario atiende muchas mascotas.
  • fecha se repite: puede haber varias consultas el mismo día.

Pero la combinación de las tres sí es única: una mascota no puede tener dos consultas con el mismo veterinario el mismo día.

La sintaxis de la PK compuesta

  pk_compuesta.sql
CONSTRAINT PK_consultas
    PRIMARY KEY (mascota_id, veterinario_id, fecha)

El orden de las columnas importa: define cómo SQL Server ordena internamente los datos. Generalmente se pone primero la columna por la que más se consulta.

¿Y si quiero un id autoincremental de todos modos?

Algunos prefieren agregar un id INT IDENTITY(1,1) PRIMARY KEY y dejar las dos FK como UNIQUE juntas. Ambas opciones son válidas:

EnfoqueVentajaDesventaja
PK compuesta (las FK juntas)No hay columna extra. El modelo es más "puro".Las consultas con JOIN son un poco más largas.
PK autoincremental + UNIQUE en las FKFácil de referenciar desde otras tablas.Agrega una columna que no aporta información de negocio.
🤓 En este cursoUsamos PK compuesta en las tablas intermedias porque es lo más común en el mundo real. Pero si en tu proyecto te piden un id numérico, ya sabes que también es válido.

El script completo

  tienda_completa.sql
-- ═══════════════════════════════════════════════════
-- TIENDA ESCOLAR: 4 tablas conectadas
-- ═══════════════════════════════════════════════════

-- Borrado seguro (en orden inverso al de creación)
DROP TABLE IF EXISTS detalle_pedido;
DROP TABLE IF EXISTS pedidos;
DROP TABLE IF EXISTS productos;
DROP TABLE IF EXISTS categorias;
DROP TABLE IF EXISTS clientes;
GO

-- ═══════════════════════════════════════════════════
-- 1. CLIENTES (padre de pedidos)
-- ═══════════════════════════════════════════════════
CREATE TABLE clientes (
    id       INT IDENTITY(1,1)
        CONSTRAINT PK_clientes PRIMARY KEY,
    nombre   VARCHAR(80) NOT NULL,
    telefono VARCHAR(20) NULL
        CONSTRAINT UQ_clientes_telefono UNIQUE
);
GO

-- ═══════════════════════════════════════════════════
-- 2. CATEGORIAS (padre de productos)
-- ═══════════════════════════════════════════════════
CREATE TABLE categorias (
    id     INT IDENTITY(1,1)
        CONSTRAINT PK_categorias PRIMARY KEY,
    nombre VARCHAR(60) NOT NULL
        CONSTRAINT UQ_categorias_nombre UNIQUE
);
GO

-- ═══════════════════════════════════════════════════
-- 3. PRODUCTOS (hijo de categorias)
-- ═══════════════════════════════════════════════════
CREATE TABLE productos (
    id           INT IDENTITY(1,1)
        CONSTRAINT PK_productos PRIMARY KEY,
    nombre       VARCHAR(80) NOT NULL
        CONSTRAINT UQ_productos_nombre UNIQUE,
    categoria_id INT NOT NULL,
    precio       DECIMAL(10,2) NOT NULL
        CONSTRAINT CK_productos_precio CHECK (precio > 0),
    cantidad     INT NOT NULL
        CONSTRAINT CK_productos_cantidad CHECK (cantidad >= 0),
    activo       BIT NOT NULL
        CONSTRAINT DF_productos_activo DEFAULT 1,

    CONSTRAINT FK_productos_categoria
        FOREIGN KEY (categoria_id)
        REFERENCES categorias(id)
);
GO

-- ═══════════════════════════════════════════════════
-- 4. PEDIDOS (hijo de clientes)
-- ═══════════════════════════════════════════════════
CREATE TABLE pedidos (
    id         INT IDENTITY(1,1)
        CONSTRAINT PK_pedidos PRIMARY KEY,
    cliente_id INT NOT NULL,
    fecha      DATETIME2 NOT NULL
        CONSTRAINT DF_pedidos_fecha DEFAULT GETDATE(),
    total      DECIMAL(10,2) NULL,

    CONSTRAINT FK_pedidos_cliente
        FOREIGN KEY (cliente_id)
        REFERENCES clientes(id)
);
GO

-- ═══════════════════════════════════════════════════
-- 5. DETALLE_PEDIDO (tabla intermedia: pedidos ↔ productos)
-- ═══════════════════════════════════════════════════
CREATE TABLE detalle_pedido (
    pedido_id       INT NOT NULL,
    producto_id     INT NOT NULL,
    cantidad        INT NOT NULL
        CONSTRAINT CK_detalle_cantidad CHECK (cantidad > 0),
    precio_unitario DECIMAL(10,2) NOT NULL
        CONSTRAINT CK_detalle_precio CHECK (precio_unitario >= 0),

    CONSTRAINT PK_detalle_pedido
        PRIMARY KEY (pedido_id, producto_id),

    CONSTRAINT FK_detalle_pedido
        FOREIGN KEY (pedido_id)
        REFERENCES pedidos(id)
        ON DELETE CASCADE,

    CONSTRAINT FK_detalle_producto
        FOREIGN KEY (producto_id)
        REFERENCES productos(id)
);
GO

E4

🏆 Reto integrador: la biblioteca del colegio

⏱ 40 min · equipos

“La biblioteca del colegio necesita registrar sus libros, los estudiantes que los piden prestados, y los préstamos realizados. Un libro puede ser prestado muchas veces a lo largo del tiempo. Un estudiante puede pedir varios libros. De cada préstamo se registra la fecha de salida y la fecha de devolución (que puede ser NULL si aún no lo ha devuelto).”

Requisitos del diseño:

  • Tabla libros con id, titulo, autor y ejemplares_disponibles.
  • Tabla estudiantes con id, nombre y ficha (UNIQUE).
  • Tabla prestamos como tabla intermedia entre libros y estudiantes, con fecha_salida, fecha_devolucion (NULL permitida).
  • Las FK correctas con las opciones de borrado adecuadas.
  • Insertar 3 libros, 2 estudiantes y 3 préstamos (uno sin devolver todavía).
✏️ Espacio de borrador del equipo: diagrama y script.
💡 Pista

La tabla intermedia prestamos puede tener un id autoincremental como PK (porque un mismo estudiante podría pedir el mismo libro dos veces en fechas distintas). Las FK apuntan a libros y estudiantes. Si se borra un estudiante o un libro, sus préstamos deben desaparecer: usa CASCADE.

🔍 Solución completa 
DROP TABLE IF EXISTS prestamos;
DROP TABLE IF EXISTS libros;
DROP TABLE IF EXISTS estudiantes;
GO

CREATE TABLE libros (
    id                    INT IDENTITY(1,1) PRIMARY KEY,
    titulo                VARCHAR(150) NOT NULL,
    autor                 VARCHAR(100) NOT NULL,
    ejemplares_disponibles INT NOT NULL
        CONSTRAINT CK_libros_ejemplares CHECK (ejemplares_disponibles >= 0)
);
GO

CREATE TABLE estudiantes (
    id     INT IDENTITY(1,1) PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    ficha  VARCHAR(30) NOT NULL
        CONSTRAINT UQ_estudiantes_ficha UNIQUE
);
GO

CREATE TABLE prestamos (
    id                INT IDENTITY(1,1) PRIMARY KEY,
    libro_id          INT NOT NULL,
    estudiante_id     INT NOT NULL,
    fecha_salida      DATE NOT NULL DEFAULT GETDATE(),
    fecha_devolucion  DATE NULL,

    CONSTRAINT FK_prestamos_libro
        FOREIGN KEY (libro_id) REFERENCES libros(id)
        ON DELETE CASCADE,

    CONSTRAINT FK_prestamos_estudiante
        FOREIGN KEY (estudiante_id) REFERENCES estudiantes(id)
        ON DELETE CASCADE,

    CONSTRAINT CK_prestamos_fechas
        CHECK (fecha_devolucion IS NULL OR fecha_devolucion >= fecha_salida)
);
GO

-- Datos de prueba
INSERT INTO libros (titulo, autor, ejemplares_disponibles)
VALUES ('Cien años de soledad', 'Gabriel García Márquez', 3),
       ('El coronel no tiene quien le escriba', 'Gabriel García Márquez', 2),
       ('La vorágine', 'José Eustasio Rivera', 1);

INSERT INTO estudiantes (nombre, ficha)
VALUES ('Valentina Ruiz', 'ADSO-123'),
       ('Carlos Peña', 'DGPH-456');

-- Valentina pide Cien años (ya devuelto)
INSERT INTO prestamos (libro_id, estudiante_id, fecha_salida, fecha_devolucion)
VALUES (1, 1, '2026-09-01', '2026-09-10');

-- Carlos pide La vorágine (sin devolver)
INSERT INTO prestamos (libro_id, estudiante_id, fecha_salida)
VALUES (3, 2, '2026-09-15');

-- Valentina pide El coronel (sin devolver)
INSERT INTO prestamos (libro_id, estudiante_id, fecha_salida)
VALUES (2, 1, '2026-09-20');

El CHECK de fechas impide que alguien registre una devolución anterior a la salida. El NULL en fecha_devolucion indica que el libro aún no ha sido devuelto. Y el CASCADE garantiza que si se borra un libro o un estudiante, sus préstamos se limpian automáticamente.

Mini glosario de esta entrega

Consulta rápida
Relación 1:1
Una fila de la tabla A se conecta con exactamente una fila de la tabla B. Se implementa con una FK UNIQUE.
Relación N:M
Muchas filas de la tabla A se conectan con muchas filas de la tabla B. Requiere una tabla intermedia.
Tabla intermedia
Tabla que contiene dos FK (una por cada extremo de la relación N:M) y resuelve la relación muchos-a-muchos.
PK compuesta
Clave primaria formada por dos o más columnas. Se declara listando todas las columnas entre paréntesis.
ON DELETE CASCADE
Al borrar una fila del padre, se borran automáticamente todas las filas del hijo que la referenciaban.
Tabla de detalle
Otro nombre para la tabla intermedia, especialmente cuando registra elementos de un documento (líneas de pedido, líneas de factura).
